# NineCube.Digital — Order Processing

An order-processing feature for a small/medium retail business: an ASP.NET Core 10 Web API, a React 18
SPA, and four roles that keep order handling and stock control apart.

**Candidate:** Yeasin Arafat · **Submission deadline:** 15 October

---

## 1. The problem this solves

The brief lists four concrete failures in the current order flow. Each one drives a specific
implementation decision rather than a general "best practice":

| Reported problem | Cause | What this implementation does |
| --- | --- | --- |
| Orders are accepted beyond available stock | Stock is validated in application code, then written in a second step | The availability rule lives **inside the UPDATE statement**. If 0 rows are affected, the whole transaction rolls back |
| Inventory becomes inconsistent when orders arrive close together | Read-then-write ("lost update") | Never read-then-write. One atomic conditional UPDATE per line, plus a `CHECK (StockQuantity >= 0)` as the last line of defence |
| Invalid requests are handled inconsistently | Errors raised ad hoc per endpoint | One error contract: RFC 7807 `ProblemDetails` + correlation id, mapped from typed domain exceptions by one middleware |
| Staff cannot see availability or order status | No single view of stock, no explicit lifecycle | Live stock badges everywhere, an explicit status lifecycle with guarded transitions, and an audit trail |

Explicitly **not** a full e-commerce platform and not an ERP. There is no payment processing, no
email, no delivery tracking and no server-side cart.

## 3. Architecture decision — why a modular monolith

One ASP.NET Core 10 Web API. One database. Five projects (Api, Application, Domain, Infrastructure,
Tests) and four modules inside them (Catalog, Inventory, Orders, Identity). No microservices, no
CQRS, no message broker, no cache.

**Why a monolith here**

1. **Order + stock must be one ACID transaction.** Placing an order decrements stock, writes order
   lines and appends an inventory ledger row. In one database that is a single `BEGIN TRAN … COMMIT`,
   and correctness is enforced by the database itself. Split across services, the same guarantee needs
   a saga or a two-phase protocol with compensation — strictly more moving parts and strictly weaker
   guarantees for a business that does not need them.
2. **Separation of duties is an ownership concern, not a deployment concern.** The fact that Staff must
   not change stock is enforced by authorization policies and by the module boundaries in code, not by
   network hops.
3. **Scope and team size are small.** A single deployable unit, one migration history, one log stream,
   one place to debug. Operational complexity is a cost, and this business does not get a return on it.
4. **The modules are still separated** by project and by namespace, and the application layer talks to
   persistence through a narrow `IAppDbContext` surface. If a module ever *needs* to become a service,
   the seam already exists.

**When microservices would actually be right**

- Several independent teams need to release on their own cadence.
- One capability needs to scale very differently from the rest (for example a high-volume checkout).
- Fault or regulatory isolation is required (payments under PCI, a separate audit boundary).
- The domain is genuinely large enough that a single deployment becomes a coordination bottleneck.

None of those hold for a small retail order feature, so they are recorded here as the trigger
conditions rather than implemented speculatively.

**Why not CQRS / event sourcing / a broker here:** the write model is small and the read patterns are
simple projections. MediatR-style indirection and a broker would add latency and operational surface
without changing a single business rule. Structured logging, a correlation id on every request and one
error contract give the observability this size actually needs.

Everything above is enforced **server side** by authorization policies on each endpoint. Role-aware
navigation and route guards in the SPA are a usability affordance only — they never replace the server
check. A customer asking for another customer's order receives **404, not 403**, so the API never leaks
whether that order exists.

### Separation of duties

The person who handles orders cannot freely modify stock. Staff can move an order through its
lifecycle but cannot create products, edit them or adjust stock; the Inventory Manager can do exactly
the opposite and cannot touch order status. The Administrator is read-only on both orders and
inventory and cannot place orders. That is enforced by four distinct role policies, and the
integration tests assert each forbidden combination returns 403.

## 5. Data model

```
Product(Id, Skuᵁ, Name, Slugᵁ, Price decimal(18,2), Currency, StockQuantity, IsActive, RowVersion,
        Description˅, ImageUrl˅, SpecsJson˅, BrandId˅, ProductLineId˅, SourceName/Url/License˅,
        PriceBasis˅, PriceVerifiedAt˅, NeedsReview)
  CHECK (StockQuantity >= 0), CHECK (Price >= 0)

Category(Id, Name, Slugᵁ, ParentId˅, Path, Depth, SortOrder, IsActive)     -- root = 1, maximum depth 4
ProductCategory(ProductId, CategoryId, IsPrimary)                          -- filtered UNIQUE index: one primary
Tag(Id, Nameᵁ) · ProductTag(ProductId, TagId)
Brand(Id, Name, Slugᵁ) · ProductLine(Id, BrandId, Name, Slug)
ProductImage(Id, ProductId, Url, IsPrimary, SortOrder)                     -- exactly one primary

Customer(Id, Name, Email) · User(Id, Emailᵁ, PasswordHash, Role, IsActive, CustomerId˅)
Address(Id, CustomerId, Label, Division, District, Upazila, AddressLine, Phone˅, IsDefault)

Order(Id, CustomerId, Status, TotalAmount decimal(18,2), CreatedAt, UpdatedAt, IdempotencyKey˅)
  UNIQUE (CustomerId, IdempotencyKey) WHERE IdempotencyKey IS NOT NULL
  CHECK (TotalAmount >= 0)

OrderItem(Id, OrderId, ProductId, Quantity, UnitPrice decimal(18,2), LineTotal decimal(18,2),
          ProductName, PrimaryCategoryName)                                 -- names and price as they were at placement
  UNIQUE (OrderId, ProductId)      -- duplicate lines are merged before insert
  CHECK (Quantity > 0)

Notification(Id, UserId, Type, Title, Body, Link˅, IsRead, CreatedAt, ReadAt˅)   -- per user, per event
InventoryMovement(Id, ProductId, OrderId˅, Delta, Reason, CreatedByUserId˅, CreatedAt) -- append-only ledger
AuditLog(Id, UserId˅, Action, EntityType, EntityId, CreatedAt, Details)
Setting(Keyᵁ, Value)                                                       -- e.g. LowStockThreshold

ᵁ unique   ˅ nullable
```

Money is `decimal(18,2)` everywhere — never `double` or `float`. Timestamps are UTC `datetime2`.

**Status flow**

```
Pending ──▶ Confirmed ──▶ Shipped
   │            │
   ├──▶ Rejected│            (Staff only; releases the stock reservation)
   └────────────┴──▶ Cancelled   (owner while Pending/Confirmed, or Staff)
```

Every illegal transition returns **409** with `code = "invalid_state_transition"`, plus `currentStatus`
and `attemptedStatus` so the client can explain itself.

**The inventory ledger is the source of truth for history.** Stock only ever moves through a guarded
statement, and each of those statements writes exactly one `InventoryMovement`, so
`opening stock + SUM(Delta) = current stock` always holds. Cancel and reject append a positive delta;
placement appends a negative one.

### Error contract

One shape for every failure: RFC 7807 `ProblemDetails`, always carrying `code` and `correlationId`.

| Status | When | Example `code` |
| --- | --- | --- |
| 400 | malformed body, failed validation, unknown product id | `invalid_request` |
| 401 | missing/expired token, bad password, deactivated account | `unauthenticated` / `unauthorized` |
| 403 | authenticated but the role is not permitted | `forbidden` |
| 404 | unknown resource, or another customer's order | `not_found` |
| 409 | not enough stock, illegal transition, duplicate SKU/email, adjustment below zero | `insufficient_stock`, `invalid_state_transition`, `duplicate_sku`, `stock_adjustment_conflict` |
| 500 | a genuine bug — never a business failure | `internal_error` |

Insufficient stock returns the exact shortfall, so the UI can show **requested vs available** per line:

```json
{
  "type": "https://ninecube.digital/problems/insufficient_stock",
  "title": "Insufficient stock.",
  "status": 409,
  "detail": "One or more items do not have enough stock available.",
  "correlationId": "15af7f07702c48ec910bdf0bbac199a7",
  "code": "insufficient_stock",
  "shortItems": [
    { "productId": 3, "sku": "NC-1003", "name": "Burr Coffee Grinder", "requested": 5, "available": 0 }
  ]
}
```

The `correlationId` is echoed in the `X-Correlation-Id` response header and pushed into every Serilog
log line for that request, so a report from a user maps onto the exact log entries.

## 7. Concurrency design

This is the core of the assessment, so it is described precisely. Nothing here relies on a read
followed by a write.

### Placing an order — one transaction, all-or-nothing

1. Validate and normalise the basket: at least one line, integer quantity 1…1000, duplicate product
   lines **merged** (so splitting 600 + 600 cannot bypass the cap).
2. Resolve the customer from the token. The body never carries a customer id.
3. Short-circuit on a previously used `Idempotency-Key`: return the original order.
4. `BEGIN TRAN`.
5. For each line **in ascending `ProductId` order** (a deterministic lock order, so two multi-line
   orders can never deadlock against each other):
   ```sql
   UPDATE Products
      SET StockQuantity = StockQuantity - @qty
    WHERE Id = @id AND IsActive = 1 AND StockQuantity >= @qty;
   ```
   `ExecuteUpdateAsync` sends that as one statement. The business rule is *in the WHERE clause*, so
   there is no window between checking and writing.
6. If any line reports **0 rows affected**, capture the true remaining stock (for the response), throw
   `InsufficientStockException`, and let the transaction dispose — **every line that already succeeded
   is rolled back**. This is what makes `Test04` (one unavailable item in a multi-item order) leave
   *all* stock untouched.
7. Otherwise insert the order, its lines (with server-side price snapshots), one negative
   `InventoryMovement` per line, and one audit row, then `COMMIT`.

Because price is snapshotted server side, a client can never influence the money.

### Status changes — exactly one winner

```sql
UPDATE Orders SET Status = 'Cancelled', UpdatedAt = @now
 WHERE Id = @id AND Status IN ('Pending','Confirmed')   -- + CustomerId = @caller for a customer
```

Zero rows affected means either the order does not exist (404) or it is not in a state that allows the
move (409). Because the status flip and the stock restore happen in the same transaction and only the
**winner** restores stock, "cancel twice restores stock only once" holds even when both requests arrive
in the same millisecond (`Test09`). The same pattern guards confirm/ship/reject.

### Stock adjustments

```sql
UPDATE Products SET StockQuantity = StockQuantity + @delta
 WHERE Id = @id AND StockQuantity + @delta >= 0;
```

Same idea: the "never below zero" rule is part of the write, so an adjustment and a concurrent order
reservation cannot overwrite each other (`Test12`).

### Idempotency

`POST /api/orders` accepts an `Idempotency-Key` header. A unique index on
`(CustomerId, IdempotencyKey) WHERE IdempotencyKey IS NOT NULL` makes the guarantee a database
invariant, not a best effort:

- a sequential replay returns the original order with **200** instead of **201**;
- two *simultaneous* identical submissions both run; the loser hits the unique index, rolls back, and
  re-reads the winner's order — stock is consumed exactly once (`Test06`);
- different customers may reuse the same key value.

After a network or 5xx failure the SPA deliberately **keeps** the same key, so an explicit retry is
still idempotent. It only generates a fresh key after a client error (400/404), which cannot succeed
on retry.

### Rejected alternatives

| Alternative | Why it was rejected |
| --- | --- |
| **Optimistic concurrency on `Product.RowVersion`** | Requires read → check → write → retry. Under the 50-way contention of `Test08` it degrades into a retry storm, and correctness depends on the retry loop being written correctly. The `RowVersion` column is kept for product *edits*, where a lost update is a UX problem rather than a stock error, but it is not the ordering mechanism. |
| **Pessimistic locks (`SELECT … WITH (UPDLOCK, ROWLOCK)` then update)** | Correct, but it holds locks for the duration of the read-modify-write and needs careful, hand-written SQL and lock-hint tuning. The conditional `UPDATE` gets the same guarantee with one statement and no lock hints to get wrong. |
| **`SERIALIZABLE` transaction** | Strongest isolation, but it takes range locks and produces deadlocks and retries under load; a victim would surface as a 500 unless every call site retried. Correctness here does not need range protection — a single-row predicate already suffices. |
| **`IsolationLevel.Snapshot`** | Would let the read and the write see different worlds and turns stock conflicts into update conflicts (3960) that still need retrying, while adding `ALLOW_SNAPSHOT_ISOLATION` to the database. It does not remove the need for the conditional write. |
| **An application-level lock / queue per product** | Does not survive a second API instance. It optimises for a single process, which is exactly the assumption the problem says is failing. |
| **`SERIALIZABLE` + retry-on-deadlock only** | Retries can still lose the race and produce confusing 409s after long waits. |

A bounded retry (three attempts, short jittered backoff) exists for genuine transient conflicts —
SQL Server deadlock victim (1205) and snapshot conflict (3960). It is safe precisely because the failed
attempt's transaction has already rolled back, so a retry can never double-apply a stock change. It is
deliberately **not** `EnableRetryOnFailure` on the DbContext, which is incompatible with the
user-initiated transactions this design depends on.

## 8. Frontend design and UX decisions

React 18 + TypeScript + Vite, React Router for routing, TanStack Query for server state. No UI
framework — hand-written CSS driven by design tokens.

- **Mid-century-modern-meets-2026 navigation bar.** A fixed pill that combines glassmorphism (a
  dark-translucent tint, `backdrop-filter: blur(18px) saturate(160%)` with the `-webkit-` prefix, and a
  1px bright translucent border) with neumorphism (raised parts — the brand dot, buttons, the selected
  tab — use *rgba* dual shadows, dark bottom-right and light top-left; pressed parts — the links
  tray and `:active` buttons — use inset rgba shadows). No solid grey shadows anywhere. The bar stays
  within `92vw`, the CTA is hidden at ≤600px, and a graceful fallback swaps in a solid tinted surface
  when `backdrop-filter` is unsupported.
- **The selected control owns its own fill.** One rule styles the active link, the opened account menu
  and the switched-on theme choice with the same amber, keyed off `aria-current`, `aria-expanded` and
  `aria-pressed`. An earlier sliding highlight measured from the active link was removed: it existed
  beside the real control's own state, so the two disagreed between themes, and a screenshot of the
  header could not be reconciled with the stylesheet.
- **A soft colourful gradient background** so the glass has something to refract. Glass and neumorphic
  surfaces are used for navigation, cards, stat tiles and the cart panel. **Dense data tables stay on
  solid, high-contrast surfaces** — readability beats decoration where the numbers are.
- **Design tokens as CSS variables** with light and dark themes via `prefers-color-scheme`, fluid type
  with `clamp()`, CSS grid/flex, and explicit checkpoints at 390 / 768 / 1024 / 1440 px.
- **Motion** is 150–300 ms on hover, press and list changes, and is disabled under
  `prefers-reduced-motion`.
- **Accessibility**: semantic HTML, visible `:focus-visible` outlines, a keyboard-operable stepper and
  navbar (arrow keys move between links), labels on every input, an `aria-live` region for results, and
  **status is never conveyed by colour alone** — every badge pairs an icon glyph with a text label.
- **Checkout safety**: the button is disabled while a request is in flight, a ref guard rejects a
  second click in the same tick, and the submission carries an idempotency key. On 409 the UI shows
  exactly which lines are short (requested vs available), refreshes stock from the server, and
  **keeps the cart** so the customer can correct it.
- **Performance**: routes are code-split (a customer never downloads the admin console), search is
  debounced at 300 ms, and TanStack Query caches with refetch on window focus and after mutations.

### The showcase at `/`

The public landing page is a scroll-driven Three.js piece: nine cards bent along a true 3D helix, two
counter-moving guide lines, an editorial title sequence, a staggered closing transition that resolves
into a responsive grid (3×2 / 2×3 / 1×6), and a light-to-dark footer blend that ends on the CTA into the
catalogue.

- It is adapted from the reference implementation at `github.com/webfueled/web-fueled-helix` (v1.1.0),
  which is vendored unchanged under `web/src/helix/reference/` — including its `VALIDATION.md`, the
  checklist the finished piece was measured against. Geometry, camera, deformation, guide lines, title
  timing and the closing-grid maths are the reference's values. The only changes are that Three.js
  comes from npm instead of a CDN, React owns the markup while an adapter owns the canvas, and the
  render loop and GPU resources are released on unmount.
- **Three.js is not in the main bundle.** It is behind a dynamic import inside the route, so a visitor
  who never opens the showcase never downloads it (measured: the scene chunk is 486 kB, the entry
  chunk 215 kB and contains none of the library — see [web/TESTING.md](web/TESTING.md)).
- **The scene is an enhancement, never a prerequisite.** Without WebGL, with
  `prefers-reduced-motion: reduce`, or if the scene fails to start, the same nine images and the same
  copy are rendered as a static grid; a failure there cannot block ordering, which lives on a separate
  route behind the auth guard.
- **It makes no API calls**, so the public landing page exposes no stock, price or customer data.

Frontend specifics — routes, how to swap the nine images, and the copy source — are in
[web/README.md](web/README.md#the-showcase).

Token storage trade-off: the access token is held **in memory** and mirrored into `sessionStorage` so a
refresh does not sign the user out. `sessionStorage` is scoped to the tab, but it is still readable by
JavaScript on this origin, so an XSS bug would expose it. The production answer is a short-lived access
token plus a refresh token in an `httpOnly`, `Secure`, `SameSite=Strict` cookie — listed under
production improvements.

## 9. Setup and run

### Prerequisites

- **.NET 10 SDK** — required. The API targets `net10.0`; install the ASP.NET Core 10 runtime.
- **Node.js 20+**
- **Docker** (for the compose database) *or* any real SQL Server instance (Express/LocalDB)
- Optional: `dotnet tool restore` for the local `dotnet-ef` tool

### Quick start (Docker — the happy path)

```bash
cp .env.example .env          # then set MSSQL_SA_PASSWORD and JWT_SIGNING_KEY
docker compose up -d          # starts SQL Server 2022 on localhost:14330 and waits for healthy
```

Apply the schema and seed, then run the two processes:

```bash
export ConnectionStrings__Default='Server=localhost,14330;Database=NineCubeOrderProcessing;User Id=sa;Password=<your password>;TrustServerCertificate=True;Encrypt=False'
export Jwt__SigningKey='<at least 32 random characters>'
export NINECUBE_SEED_PASSWORD='<the password for the four demo accounts>'

dotnet run --project src/NineCube.Api         # http://localhost:5080  (Swagger at /swagger)
```

## 12. Assumptions

Recorded here because the brief left them open.

1. **The API does not allow anonymous browsing, and neither does the catalogue.** Every `/api/products`
   endpoint requires authentication, because live stock levels are commercial information, so `/products`
   sits behind the login page. The one public screen is the showcase at `/`, which makes no API calls
   and shows no stock, price or customer data — a marketing page, not a leak.
2. **The cart is client-side only.** There is no server cart table. Stock is reserved at *placement*,
   not at *add-to-cart*, which is the only point at which a promise can actually be kept.
3. **Payment happens outside the system.** There is no payment step, and therefore no "payment
   verification". Orders start as `Pending` and are confirmed by Staff.
4. **Reservation at placement, not at confirmation.** Stock is decremented when the order is placed,
   and released on cancel/reject. This is what stops two customers from both "winning" the last unit.
5. **`Idempotency-Key` is optional at the API level, always sent by the SPA.** A caller that omits it
   gets no deduplication; the SPA generates one UUID per submission attempt.
6. **Order status changes are Staff-only.** Administrators read everything but change no order status
   and no stock, and cannot place orders.
7. **The low-stock threshold is a database value** (`Setting` table, default 5), editable by the
   Administrator. It is exposed read-only to every authenticated role so stock labels agree everywhere.
8. **The inventory ledger is append-only** (out of scope: correcting a historical movement).
9. **Product updates carry a `RowVersion`** for optimistic concurrency on edits; it is not the ordering
   mechanism (see §7).
10. **Access tokens are short-lived (30 minutes) with no refresh token yet.** Every authenticated
    request re-reads the user's role and active flag from the database, so a role change or a
    deactivation takes effect immediately instead of waiting for the token to expire.
11. **Registration always creates a Customer.** There is no self-service role selection; roles are
    assigned by an Administrator.
12. **The shop prices in Bangladeshi taka, and the UI is English.** Amounts are stored as
    `decimal(18,2)` and rendered with `Intl.NumberFormat('en-BD', …, currencyDisplay: 'code')`, so
    1490 becomes `BDT 1,490.00` everywhere. Each product and each order line still carries its own
    `Currency` column, and new products default to `BDT`. A handful of the original demo rows are
    legacy `USD` and are left honest rather than silently repriced — the cart will not add a taka item
    to a dollar basket, it tells you to place them as two orders. Sales reporting labels its revenue
    with the currency it actually totalled.
13. **Timestamps are UTC** end to end. They are stored as UTC, and the API serialises them with an
    explicit `Z` (`2026-10-13T19:51:50.848Z`) through one JSON converter, because an offset-less
    value is re-read by a browser as *local* time — which silently shifted every timestamp by the
    viewer's UTC offset. The SPA renders them in the browser's own time zone.
14. **Report ranges are calendar dates in the viewer's time zone.** The `From`/`To` inputs default to
    the last 30 days *ending today locally* and are converted to an inclusive UTC instant range at the
    edges (`00:00:00` local → `23:59:59` local), so "today" is never empty just because the server
    runs in UTC.
15. **One database, one deployment unit.** See §3.
16. **Staff navigation is Showcase / Products / Orders / Sales.** The brief's "Staff" link maps to the
    staff order console plus its read-only sales summary; `My Orders` remains a customer-only page.
17. **Deactivating the last active administrator is refused** (409), so the system cannot be locked out
    of its own administration.
18. **A seeded product's opening stock is not written to the ledger**, because seeding sets a starting
    balance rather than a movement. Every movement *after* seeding balances exactly.
19. **Only a Customer sees ordering controls.** Staff, Inventory Managers and Administrators get a
    read-only catalogue: no stepper, no "Add to cart", no cart panel. The API refuses the call anyway
    (403), but the UI never offers an action that would be rejected.
20. **The catalogue moved from `/` to `/products`,** because the brief asks for the showcase at the root.
    A link to `/` now opens the showcase; the showcase's closing CTA leads to `/products`, and signing in
    with no pending destination lands there too. A wrong-role visit is redirected to `/products` with a
    notice rather than to the showcase, so the notice has somewhere to render.
21. **The shell footer is hidden on `/`,** because the showcase ends with its own dark footer blend;
    stacking a light footer under it would break that section.
22. **The showcase's nine images come from `web/public/assets`, in filename order,** counted into
    `assets.json` by `web/scripts/asset-manifest.mjs` (run automatically before `dev` and `build`). Vite
    cannot enumerate a public directory from application code, so a generated manifest is what lets the
    artwork be replaced by dropping files in, with no code change. Fewer than nine images repeat in
    order; the nine shipped files are the reference's demo artwork, since no brand imagery was supplied.
23. **The brief's text placeholders are resolved in one file** (`web/src/helix/showcaseCopy.ts`): the
    opening heading is NineCube.Digital, the titles are `DESIGN +` and `MOTION`, and the closing footer
    text plus the CTA caption are set there. The reference's transition title is deliberately unchanged.

## 13. Limitations (explicitly out of scope)

- **No payment processing and no payment verification.** No card data, no PSP integration, no
  reconciliation. A real deployment would add an outbox + webhook confirmation; the order lifecycle
  would gain a `Paid` step, and stock release would have to account for payment timeouts.
- **No email or SMS delivery.** The in-app inbox at `/notifications` is implemented and is written from
  the domain events (placement, status change, a low-stock crossing). Its preferences panel — per-type
  channels and quiet hours — is stored in this browser only, and is honest about that, because nothing
  leaves the system: a password reset cannot be sent by mail, and an order confirmation is only as
  timely as the customer's next visit. Delivering those messages through an outbox, with preferences on
  the server, is listed under production improvements.
- **No delivery tracking.** `Shipped` is a terminal status; carrier integration, tracking numbers and
  partial shipments are out of scope.
- **No returns or refunds.** A returned item would need a new movement type and a restocking policy.
- **No rate limiting or WAF.** Throttling on `/api/auth/login` and `/api/orders` belongs at the edge.
- **No refresh tokens.** See assumption 10.
- **No caching layer.** Deliberate: the read volume does not justify the invalidation risk on
  stock-sensitive data.
- **No soft-delete or GDPR erasure workflow.** Users are deactivated, not deleted, so history stays
  intact.
- **No multi-warehouse, multi-currency or tax handling.**
- **Backups** are a database-level operations procedure, not an application feature — see below.

### Backups (operations procedure, not application code)

The application does not manage backups, and it does not need to in order to be correct. The production
procedure is a SQL Server responsibility:

- `FULL` backup nightly, `DIFFERENTIAL` every 6 hours, `LOG` every 15 minutes, retained for 30 days;
- restore drills quarterly into a scratch instance, and the restore verified with
  `RESTORE VERIFYONLY` plus a row-count and ledger-sum check
  (`SELECT ProductId, SUM(Delta) FROM InventoryMovements GROUP BY ProductId`) reconciled against
  `Products.StockQuantity`;
- backups encrypted at rest, stored in a separate account/region from the database;
- point-in-time restore is what makes "we can undo a bad data migration" possible.

Because stock is only ever changed by a guarded statement that also appends a ledger row, a restored
database is internally reconcilable — the ledger can be used to prove that the restored stock is
consistent.

## 14. Production improvements

In rough order of value.

1. **Payments + verification.** A hosted payment intent, an outbox-backed webhook handler, and a
   `PaymentStatus` on the order. Idempotent webhook processing keyed by the provider's event id.
2. **Transactional outbox** for notifications and downstream integrations, so a mail or webhook outage
   can never roll back an order — and consumers get at-least-once delivery with deduplication.
3. **Refresh tokens + `httpOnly` cookies**, rotating, with reuse detection. Access tokens down to a few
   minutes. Removes the `sessionStorage` trade-off entirely.
4. **Rate limiting** (`AspNetCore.RateLimiting`) per IP and per account on `/api/auth/login`, plus per
   customer on `POST /api/orders`. Add account lockout/backoff after repeated failures.
5. **Reservations with a TTL.** A basket that is never confirmed currently holds stock indefinitely.
   A `ReservationExpiresAt` column plus a background sweeper (or a `Pending` timeout) would release it,
   with the same exactly-once discipline as cancel/reject.
6. **Observability that earns its keep.** OpenTelemetry traces spanning SPA → API → SQL, metrics for
   order rate, 409 rate by reason, p95 placement latency and stock-conflict ratio, and alerting on the
   ratio rather than on individual errors.
7. **CI/CD.** Build, `dotnet format --verify-no-changes`, unit + integration tests against a container
   SQL Server, frontend typecheck/tests, Playwright smoke on a preview deployment, then a gated
   migration step. Migrations applied as a separate, idempotent release stage — never by the app on
   start-up in production.
8. **Idempotency key retention policy.** Keys are currently kept forever; a documented retention window
   plus a cleanup job keeps the unique index small.
9. **Hardened secrets**: a managed vault instead of environment files, with rotation.
10. **Concurrency load testing** in CI (the 50-way stress test at a larger scale) to keep the design
    honest as the catalogue grows.

## 16. What was added after the first version

The first version was the order-processing feature on .NET 8 with a ten-product coffee catalogue.
What follows is the rest of the work, told in the order it landed. The numbers in each paragraph are
the state of this repository, not of the original brief.

### Moving to .NET 10, and pricing in taka

Every project now targets `net10.0`; ASP.NET Core and EF Core are on 10.0.13 and the SQL Server client
on 6.1.7, which supersedes the .NET 8 target in the original assessment. Run
`dotnet tool restore --tool-manifest dotnet-tools.json` after pulling, because the local `dotnet-ef`
tool is pinned there, and use `net10.0` for any launch command. The additive `ProductMedia` and
`ProductProvenanceAndCurrency` migrations are applied when the API starts.

Money is displayed in Bangladeshi taka, `BDT 1,490.00`, from one formatter in
`web/src/lib/helpers.ts`, and `Product.Currency` defaults to `BDT`. The original demo products and their
orders keep the USD figures they were created with rather than being silently repriced — assumption 12
explains what the cart does when the two currencies would meet in one basket.

### The catalogue, the categories and the brands

The product data is no longer a sample feed. `seed/` is an independent pipeline that reads from the
approved sources listed in `SEED_REPORT.md`, cleans the records, and loads them into SQL Server
insert-only: a rerun never updates a product that already exists, so repeated runs are exact no-ops.
The result is 145 clean catalogue rows in the latest inserting run and 171 products in the database,
with 32 tags and 186 category links. Provenance and the review queue are recorded per product in
`SEED_REPORT.md`. Every generic fallback carries `needs_review = true` and cites a Wikipedia product-type
page for background only, never a brand, model or price. The older development convenience — a small
kitchen sample pulled from DummyJSON so a fresh database was never empty — is still present as an
import-if-missing step for a database with no `DJ-` SKUs, and it is the only place in the system where a
product is invented rather than attributed.

Categories are a real hierarchy: unique slug, sibling-name uniqueness, materialized paths, depth
(root = 1, maximum = 4), ordering and activity, with one primary category per product enforced by a
filtered index. Mutations run in a transaction under an application lock; a rename or a move recomputes
the whole subtree, a cycle or an duplicate is refused with the reason as RFC 7807, and deleting an
occupied category requires a reassignment target whose own descendants are rejected. None of it can
move a stock figure, and there are tests that assert that. Order lines snapshot the product name and
primary category at placement, so a later rename does not rewrite an invoice.

Brand and series became entities of their own, derived from the attributed data rather than from a
name pattern that might invent a model that does not exist. `GET /api/brands` and
`GET /api/brands/{slug}/lines` feed the filter panel, facet counts are computed with the other active
filters applied, and the bulk `assign-brand` action moves a series with its brand or refuses.

The catalogue screen was rebuilt around that: a category tree with counts that sticks below the header
while only its own body scrolls, the sort controls as radio rows inside the panel rather than native
selects the scroll area clipped, price fields and slider kept in step, and every control written into
the URL so a view survives a reload, a bookmark and the Back button. Chips on a card are shortcuts that
add that filter instead of replacing the ones already applied.

### The work each role does

Staff got a category editor and an order console that classifies work into queues — to confirm, to
ship, invoices and history — with a bulk review that applies a decision to the selected orders,
reports the ones the server refused without failing the batch, and sends nothing at all when the review
is dismissed. Bulk product editing went in on the same terms, with one deliberate exception: stock is
never part of a bulk edit. A stock change stays a single-product, signed, reason-carrying update whose
availability rule lives inside the `UPDATE`, because that is the one place the promise can be kept.

Customers got the pages the first version assumed they would have: `/account` summarising their orders
and spending in BDT, `/account/profile` for name, phone, password and a saved-address book with exactly
one default, and `/notifications` as a real inbox with unread filters, bulk mark-as-read and a
preferences panel. The inbox is server data — one `Notification` row per user per event, with the five
types `OrderPlaced`, `OrderStatusChanged`, `OrderCancelled`, `NewOrder` and `LowStock`. The preferences
are deliberately browser-local (`localStorage`), because there is no delivery channel to configure yet:
toggling "email" off changes nothing server-side until an outbox exists. The API behind the pages is
`/api/me` and `/api/notifications`; another customer's record answers `404`, not `403`, so neither
endpoint can be used to probe what exists.

Notifications are written where the event happens — placement, status change, a low-stock crossing —
and are deliberately absent for a rejection that never took place. A low-stock notice for the same
product is written once rather than on every movement.

### Appearance, and what was measured to prove it

The supplied cube mark is paired with a readable wordmark in one shared `Brand` component used by the
navigation, the sign-in page, invoices and the footer, on transparent backgrounds with theme-aware
colours instead of a white tile. Light mode got opaque white surfaces, quieter page background, stronger
input borders and darker orange branding. Appearance is three icon buttons — monitor for System, sun for
Light, moon for Dark — with the active choice exposed through `aria-pressed`, applied before React
renders so there is no flash, and kept across reloads.

The second pass over appearance was measurement rather than opinion, and it is written up defect by
defect in [FIX_REPORT.md](FIX_REPORT.md): translucent surfaces sampled from composited pixels, the
selected navigation state certified at 5.27:1 in light and 5.72:1 in dark, row action buttons that had
gone invisible on their own tables, modal headers that pushed the dialog open instead of wrapping, a
card chip that read as a hole in the card rather than the filter it applies, and a shared depth
treatment for tiles, charts and tables that switches itself off under reduced motion. Each one now has
both a stylesheet contract test and a browser test that reads rendered pixels.

### The showcase at `/`

`/` is a public, scroll-driven Three.js scene: nine cards bent along a helix, two counter-moving guide
lines, an editorial title sequence, a closing transition into a responsive grid, and a light-to-dark
footer blend that ends on the way into the catalogue. The catalogue moved to `/products`, so the
showcase is the only route the reference markup lives on and the only screen that makes no API call.

It is adapted from `github.com/webfueled/web-fueled-helix` v1.1.0, vendored under
`web/src/helix/reference/` so the comparison can be repeated: geometry, camera, deformation, depth
ordering, title timing and the closing-grid breakpoints are the reference's own values. Three.js comes
from npm rather than a CDN and sits behind a dynamic import inside the route, so the main bundle
contains no `WebGLRenderer`; measured from the production build the scene chunk is 486.62 kB
(gzip 124.56 kB) against a 214.81 kB entry (gzip 69.30 kB). React owns the markup, an adapter owns the
canvas, and the render loop, listeners, geometries, materials, textures and WebGL context are released
on unmount.

The scene is an enhancement, never a requirement: without WebGL, under `prefers-reduced-motion: reduce`,
or if the scene throws, the same nine photographs and the same copy render as an accessible static grid
(3×2, 2×3, 1×6), and ordering, which lives behind the auth guard, is unaffected. Card artwork is
enumerated from `web/public/assets` in filename order through a generated manifest, and the brief's text
placeholders are resolved in one file; both are documented with the swap procedure in
[web/README.md](web/README.md#adding-images).

To run it from a clean copy: put a real `.env` beside this README (the values `.env.example` names),
start SQL Server — `docker compose up -d` for the container on port 14330, or LocalDB — then
`dotnet run --project src/NineCube.Api` and `cd web && npm ci && npm run dev`. Section 11 has the test
commands in the order they are worth running.
